# Деплой на Hetzner через GitHub Actions

Пуш у гілку `claude/dental-booking-service-aorx3i` автоматично білдить усі
5 застосунків і деплоїть їх на сервер (`.github/workflows/deploy.yml`).
CI сам ставить Node/PostgreSQL/nginx/certbot, накатує міграції і рестартує
сервіси — все, що потрібно від тебе, це один раз виконати кроки нижче.

## Чому так, а не напряму з цієї сесії

Я (Claude, у цій сесії) технічно не можу підключитись по SSH до довільного
зовнішнього сервера — мережева політика цього sandbox-середовища блокує
вихідний трафік на порт 22 і будь-які HTTPS-запити на неавторизовані хости
(перевірено: `nc` на порт 22 таймаутиться, HTTPS через проксі повертає 403
policy denial). GitHub Actions runners такого обмеження не мають — тому
весь фактичний деплой виконує саме GitHub, а не я напряму.

## Крок 1: додай публічний ключ на сервер

На сервері (178.105.185.67), під root, додай у `~/.ssh/authorized_keys`:

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIEKu46rlCHGYmf1pV4FS80KVoxJ5UDl8lvmy/onIUZi1 github-actions-deploy@galactic-dent
```

Це **окремий** ключ, згенерований спеціально для GitHub Actions (не той,
яким я намагався підключитись раніше) — використовується лише для деплою,
легко відкликати/замінити пізніше.

## Крок 2: додай секрети в GitHub

Репозиторій → Settings → Secrets and variables → Actions → New repository
secret. Потрібні:

| Secret | Значення |
|---|---|
| `DEPLOY_SSH_KEY` | приватний ключ (весь блок нижче, разом з `BEGIN`/`END`) |
| `DEPLOY_HOST` | `178.105.185.67` |
| `DEPLOY_USER` | `root` |
| `TELEGRAM_BOT_TOKEN` | токен @Galactic_dent_bot від @BotFather (юзернейм бота — стара назва; змінити його можна лише в @BotFather) |
| `POSTGRES_PASSWORD` | будь-який новий надійний пароль для БД (сам його вигадай, ніде більше не використовується) |
| `LETSENCRYPT_EMAIL` | твій email — для сповіщень Let's Encrypt про сертифікат |
| `ANTHROPIC_API_KEY` | опційно — якщо не задаси, асистент працює на rule-based fallback |
| `STAFF_CHAT_ID` | опційно — Telegram chat id асистентки для push про "Гострий біль" |

Приватний ключ для `DEPLOY_SSH_KEY` — **навмисно не в цьому файлі**
(приватний ключ ніколи не повинен потрапляти в git, навіть у приватний
репозиторій — історію коміта важко повністю стерти). Я вставив його прямо
в чат окремим повідомленням — скопіюй його звідти. Після того як вставиш
у GitHub Secret, вважай цей приватний ключ "витраченим" з мого боку — я
більше не буду його показувати; сам GitHub Secret після збереження ніхто
(включно зі мною) не може прочитати повторно, лише перезаписати новим.

## Крок 3: перевір DNS

`galactic.swipescape.eu` має вказувати на `178.105.185.67` (A-запис). Без
цього Let's Encrypt не зможе видати сертифікат і certbot впаде з помилкою.

## Крок 4: запусти деплой

Досить будь-якого пуску в `claude/dental-booking-service-aorx3i` — або
запусти вручну: GitHub → Actions → "Deploy GalaClinic" → Run workflow.

Перший прогін триває довше (ставить Node/Postgres/nginx/certbot з нуля,
видає TLS-сертифікат) — стеж за логом у вкладці Actions. Наступні пуші вже
швидкі (лише білд + rsync + restart).

## Що ти отримаєш після успішного деплою

| URL | Що це |
|---|---|
| `https://galactic.swipescape.eu/` | Сайт клініки |
| `https://galactic.swipescape.eu/admin/` | Admin-панель (наразі без авторизації — див. нижче) |
| `https://galactic.swipescape.eu/app/` | Telegram Mini App |
| `https://galactic.swipescape.eu/api/` | Backend API |

Постав `WEBAPP_URL` у @BotFather (`/setmenubutton` або просто перезапусти
бота — `telegram-bot` сам виставляє menu button і кнопку в головному меню
на `https://galactic.swipescape.eu/app/`, якщо `WEBAPP_URL` заданий — а він
тепер заданий автоматично через `remote-deploy.sh`).

## Важливо перед реальним використанням пацієнтами

* **Admin-панель (`/admin/`) зараз відкрита без авторизації.** Будь-хто, хто
  знає URL, може її відкрити. Це прийнятно для тестування, але перед тим як
  давати доступ реальним пацієнтам — обов'язково додати логін лікарю/
  асистентці, перш ніж афішувати домен публічно.
* `POSTGRES_PASSWORD` генерується в GitHub Secret і ставиться в БД під час
  першого деплою — якщо колись зміниш секрет ПІСЛЯ першого деплою, стара БД
  і новий пароль розійдуться (`ALTER USER` в скрипті це виправляє автоматично
  при наступному деплої, тож зміна пароля пізніше теж безпечна).
* Nginx-конфіг деплоїться лише один раз (`remote-deploy.sh` не перезаписує
  його, якщо файл вже є) — це щоб не затирати те, що certbot дописує в
  конфіг для HTTPS. Якщо колись знадобиться змінити маршрутизацію nginx,
  редагуй `/etc/nginx/sites-available/galactic-dent.conf` на сервері
  напряму (або видали файл і задеплой знову, потім перезапусти certbot).
