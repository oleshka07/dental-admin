# GalaClinic — booking system + website (MVP)

Реалізація з `Dental_Clinic_CRM_Specification_v2.md`: backend + rule engine,
Telegram-бот, admin-панель, і публічний сайт клініки з вбудованим віджетом
онлайн-бронювання та AI-асистентом на кожній сторінці.

**Продакшн-деплой** на Hetzner через GitHub Actions (push → авто-деплой) —
див. [`DEPLOY.md`](./DEPLOY.md).

## Структура

```
backend/       Fastify + Prisma + PostgreSQL API (пацієнти, типи візитів,
                правила розкладу, винятки, записи, лист очікування, AI-асистент,
                верифікація Telegram Mini App initData)
telegram-bot/  Telegraf-бот для пацієнтів (CZ/UA), викликає backend API,
                відкриває Mini App через inline-кнопку і menu button
telegram-app/  Telegram Mini App (Vite+React) — повний функціонал booking-
                віджету нативно всередині Telegram
admin-web/     React-адмінка для лікаря/асистента (календар, шаблони, записи)
site/          Next.js сайт клініки GalaClinic — контент + віджет
                бронювання + AI-чат на всіх сторінках
```

## Запуск локально

### 1. База даних

Локально (без Docker):

```bash
sudo pg_ctlcluster 16 main start
sudo -u postgres psql -c "CREATE USER dental WITH PASSWORD 'dental' CREATEDB;"
sudo -u postgres psql -c "CREATE DATABASE dental_admin OWNER dental;"
```

Або через Docker: `docker compose up -d postgres` (потребує робочого Docker
daemon).

### 2. Backend

```bash
cd backend
cp .env.example .env
npm install
npx prisma migrate dev --name init
npx prisma db seed        # заповнює приклад правил лікаря з ТЗ
npm run dev               # http://localhost:3000
```

Опціонально: додайте `ANTHROPIC_API_KEY` у `backend/.env`, щоб AI-асистент
на сайті відповідав через Claude замість rule-based fallback-логіки (без
ключа асистент повністю працює, просто відповідає за наперед заданими
правилами/фактами про клініку).

Для Mini App (`telegram-app/`) обов'язково додайте `TELEGRAM_BOT_TOKEN` у
`backend/.env` — **точно той самий токен**, що і в `telegram-bot/.env`
(`BOT_TOKEN`). Бекенд використовує його, щоб перевіряти криптографічний
підпис (HMAC-SHA256) кожного запиту з Mini App — без цього Mini App працювати
не буде (усі запити повертатимуть 401).

### 3. Telegram-бот

```bash
cd telegram-bot
cp .env.example .env      # вписати BOT_TOKEN від @BotFather і STAFF_CHAT_ID асистентки
npm install
npm run dev
```

Якщо задати `WEBAPP_URL` (публічний HTTPS-домен, де задеплоєний `telegram-app/`),
бот покаже кнопку "📱 Otevřít aplikaci" в головному меню і встановить її як
персистентну menu-button. **Важливо:** Telegram Mini Apps вимагають публічний
HTTPS URL — `localhost` всередині реального Telegram-клієнта не працює.

### 4. Admin-панель

```bash
cd admin-web
cp .env.example .env
npm install
npm run dev                # http://localhost:5173
```

### 5. Сайт клініки (Next.js)

```bash
cd site
cp .env.example .env.local
npm install
npm run dev                # http://localhost:3000 (запустіть на іншому порті,
                            # якщо backend вже займає 3000: PORT=4000 npm run dev)
```

### 6. Telegram Mini App

```bash
cd telegram-app
cp .env.example .env.local
npm install
npm run dev                # http://localhost:5174
```

**Тестування поза реальним Telegram.** Оскільки Mini App отримує ідентичність
пацієнта через криптографічно підписаний `initData`, який у справжньому
Telegram підписує сам клієнт, локально в звичайному браузері його ніде
взяти. Для розробки:

```bash
cd telegram-app
TELEGRAM_BOT_TOKEN=<той самий токен, що в backend/.env> node scripts/generate-test-init-data.mjs
```

Скрипт виведе валідний підписаний рядок — відкрийте
`http://localhost:5174/?devInitData=<цей рядок, URL-encoded>`. У dev-режимі
застосунок сам підставляє легкий емулятор `window.Telegram.WebApp`
(`src/telegram/devStub.ts`) з видимими MainButton/BackButton внизу/вгорі
екрана — він ніколи не потрапляє у продакшн-білд. Для реального тестування
всередині Telegram потрібен публічний HTTPS-домен (`WEBAPP_URL` у
telegram-bot, і той самий домен задеплоєний з `telegram-app/dist`), інакше
Telegram відмовиться відкривати Mini App.

## Демо-дані для показу

Щоб систему можна було показати живою — заповнений календар, історія візитів,
пацієнти в адмінці — є генератор демонстраційного набору.

```bash
cd backend
npm run demo:seed     # ~40 пацієнтів + записи за 8 тижнів назад і 4 вперед
npm run demo:purge    # прибрати весь демо-набір
```

**Як це позначено.** Дві ознаки:

* `Patient.isDemo` — згенеровані пацієнти й усе, що на них висить;
* `Appointment.isDemo` — окремо на записах, бо демо-історія може бути прив'язана
  до **справжнього** пацієнта (власника `DEMO_TELEGRAM_ID`), чий запис має
  пережити очистку, а ці візити — ні.

`demo:purge` видаляє рівно цей набір і не може зачепити справжній.
Додатково демо-записи легко впізнати на око:

| Поле | Значення |
|---|---|
| `phone` | `+420999xxxxxx` — діапазон 9xx не виданий чеським операторам, тож номер не може збігтися з реальним |
| `telegramId` | `demo-N` — Telegram ID завжди числові, тож колізія з живим акаунтом неможлива |
| `notes` | починається з `[DEMO]` |

В адмінці такі рядки мають жовтий бейдж **DEMO**, а на вкладках «Pacienti» і
«Návštěvy» є перемикач «Skrýt demo data».

**Що набір не чіпає.** Типи візитів і шаблони розкладу — це справжня
конфігурація клініки, вони не позначені як демо і переживають `demo:purge`.
Якщо їх у базі ще немає, `demo:seed` створює базовий набір за опублікованими
годинами роботи (Po–Čt 8:00–17:00, Pá 8:00–14:00, перша година дня — на
гострий біль). Наявну конфігурацію скрипт ніколи не перезаписує.

Майбутні слоти заповнені приблизно на третину — навмисно, щоб на демонстрації
можна було пройти сценарій запису до кінця, а не впертися в «немає вільних
термінів».

**Прив'язка до реального Telegram.** Щоб Mini App відкривався з готовою
історією візитів, а не з екрана реєстрації, передайте свій Telegram ID:

```bash
DEMO_TELEGRAM_ID=123456789 npm run demo:seed
```

Свій ID можна дізнатися, надіславши боту команду `/whoami`.

Якщо цей ID уже комусь належить — а зазвичай так і є, бо той, хто показує
систему, колись реєструвався через Mini App — скрипт **не забирає** ID у цього
запису. Справжній пацієнт лишається недоторканим і просто отримує демо-історію
візитів. Тому позначка стоїть і на самих записах (`Appointment.isDemo`), а не
лише на пацієнтові: `demo:purge` прибирає ці візити, але сам акаунт не чіпає.

**Запуск на сервері.** Два способи, обидва — явні:

* GitHub Actions → workflow «Deploy GalaClinic» → *Run workflow*, і в полі
  `demo_data` вибрати `seed` або `purge` (за потреби заповнити
  `demo_telegram_id`);
* або маркер у повідомленні коміту: `[demo-seed]` / `[demo-purge]`. Це той
  самий свідомий вибір, просто доступний автоматизації, яка має право пушити,
  але не має права на `workflow_dispatch`. Якщо в повідомленні є обидва
  маркери, виграє `purge`.

Звичайний `git push` без маркера набір не чіпає ніколи.

CI передає скриптові `DEMO_SHOWCASE_LATEST=1` — тоді показовим акаунтом стає
**останній зареєстрований через Telegram справжній пацієнт**, і особистий
Telegram ID не потрібно класти в цей публічний репозиторій. Це розраховано на
період до запуску: поки система не відкрита для пацієнтів, найновіший такий
акаунт — це той, хто її налаштовував. Після запуску передавайте явний
`DEMO_TELEGRAM_ID`.

## Що вже реально працює (перевірено end-to-end)

* **Rule Engine**: тижневі шаблони (`SlotTemplate`) генерують конкретні слоти;
  ручне закриття (`SlotException`) і вже існуючі записи (`Appointment`)
  коректно віднімаються. Seed відтворює точний приклад лікаря: чт 07:00–09:00
  тільки "Akutní bolest", пт 08:00–10:00 "Zákrok", вт/ст/чт 16:00–17:00
  "Preventivní prohlídka".
* **Захист від подвійного бронювання**: створення запису йде в транзакції з
  serializable isolation і повторною перевіркою вільного слоту.
* **Telegram-бот**: вибір мови (CZ/UA), реєстрація пацієнта зі згодою на
  обробку даних, бронювання за типом візиту, окрема гілка "Гострий біль"
  (питання → пошук найближчого акутного слоту → якщо немає, заявка
  `NEEDS_CALL` + push-повідомлення асистентці в Telegram), перегляд/скасування
  своїх записів.
* **Admin-панель**: тижневий календар з кольорами статусів і вільними
  слотами, закриття слоту в один клік, конструктор шаблонів розкладу,
  список записів з фільтрами за статусом/типом/датою.
* **Сайт GalaClinic** (`site/`): 5 сторінок (Domů, O nás, Služby a ceník,
  MDDr. Galaktionov, Kontakty) з реальним контентом клініки, брендингом за
  логотипом і Sokolov-bridge блоком для колишніх пацієнтів.
* **Booking-віджет на сайті**: модальне вікно, доступне з будь-якої сторінки
  (кнопки в хедері, hero, картках послуг, floating-кнопки) — вибір типу
  візиту → реальні вільні слоти з rule engine → контактні дані + згода на
  обробку даних → підтверджений запис у тій самій БД, що й Telegram-бот і
  адмінка. Окрема гілка "Акутний біль" з описом симптомів і escalation-запитом,
  коли поруч немає вільного слоту.
* **AI-асистент на кожній сторінці**: плаваюча чат-бульбашка, привітання й
  контекст залежать від поточної сторінки (послуги/про лікаря/контакти).
  Використовує Claude API, якщо заданий `ANTHROPIC_API_KEY`, інакше —
  rule-based fallback на реальних фактах клініки (адреса, години, страховки).
  Ніколи не ставить діагноз; при описі болю чи наміру записатися пропонує
  кнопку, яка одразу відкриває booking-віджет. Усі діалоги логуються в
  `ConversationLog` для подальшого рев'ю лікарем.
* **Telegram Mini App** (`telegram-app/`): повноцінний застосунок всередині
  Telegram — реєстрація (з автозаповненням імені з профілю Telegram),
  бронювання (без повторного вводу контактів — ідентичність вже відома),
  гілка "Акутний біль", "Мої візити" зі скасуванням, чат з AI-асистентом.
  Використовує нативні Telegram MainButton/BackButton замість власних кнопок,
  тему (світла/темна) з `themeParams`. **Кожен запит криптографічно
  верифікується на бекенді** (HMAC-SHA256 підпису `initData` за офіційним
  алгоритмом Telegram) — пацієнт фізично не може скасувати чи побачити
  запис іншого пацієнта, підмінивши свій telegram id на клієнті; перевірено
  тестом (чужий підпис і підроблені дані відхиляються 401, спроба скасувати
  чужий запис — 403).

## Свідомо не входить у цей інкремент (наступні кроки)

* Автонагадування 24h/2h і "живий" лист очікування (модель `WaitlistEntry`
  вже є в API, автоматичного опитування пацієнтів ще немає).
* WhatsApp Business API, SMS, voice-автовідповідач — Фаза 3, за бюджетом і
  результатами використання перших фаз.
* Авторизація в admin-панелі (зараз API відкритий без токена — обов'язково
  додати перед реальним запуском, ordinace матиме доступ в мережу).
* Синхронізація з існуючим календарем лікаря (чекаємо деталей, які лікар
  дасть окремо).
* Повний переклад сайту на UA/EN (зараз контент чеською — основна мова
  ринку; booking-віджет уже підтримує вибір мови пацієнта CZ/UA).
* Реальні номер телефону/e-mail клініки і фото інтер'єру/команди — зараз
  плейсхолдери, легко замінити в `site/src/lib/content.ts`.
* `next@14.2.35` все ще тягне вразливу транзитивну `postcss` (build-time
  only, не рантайм-загроза); повне усунення вимагає мажорного апгрейду на
  Next 16 — окрема задача.
* Mini App просить телефон текстовим полем (як і сайт/класичний бот), а не
  через нативний `requestContact` (Telegram надсилає контакт боту як
  повідомлення, не напряму в JS застосунку — це вимагає async-очікування,
  яке додає крихкості без реальної користі для одноразової реєстрації).
* Mini App поки не отримує push-нагадувань напряму — нагадування 24h/2h
  (коли будуть реалізовані) прийдуть через звичайні повідомлення бота, як і
  для класичного флоу.
